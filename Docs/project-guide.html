Architecture

Layer dependencies

  • Domain — entities, enums, CronExpression VO, domain events. Zero dependencies (only Cronos).
  • Application → Domain. CQRS (MediatR), FluentValidation, AutoMapper, pipeline behaviors, all service interfaces.
  • Infrastructure → Application + Domain. EF Core/Npgsql, Hangfire (scheduler + Postgres store), command execution, JWT, SMTP, repositories.
  • Api → everything. Controllers, middleware, DI composition root, Hangfire dashboard, static UI in wwwroot.

Key patterns

  • Domain events — entities collect events; ApplicationDbContext.SaveChangesAsync flushes them as MediatR notifications after the write.
  • MediatR pipeline — LoggingBehavior (outermost: correlation id, OTel span, slow-request warn) → ValidationBehavior → handler.
  • CQRS — 8 commands + 6 queries, each an isolated handler; validators on create/update/login/register.
  • Hangfire — recurring job id = task GUID; in-process server; Postgres job store.
  • Soft delete — IsDeleted flag; repositories filter it out; fired jobs for deleted tasks no-op.

ℹ
Retry logic: every failure does RetryCount++. While RetryCount ≤ MaxRetries the task stays Active and a delayed Hangfire job re-runs it after min(300, 2^RetryCount × 30) seconds → 60 s, 120 s, 240 s, then 300 s. Once the budget is exceeded: task → Failed, TaskFailedEvent fires → error log + admin email. A success resets RetryCount to 0.

Execution engine & retry

How a command runs

  • Windows → cmd.exe /c <command>; Linux → /bin/sh -c "<command>"
  • stdout & stderr read concurrently (no pipe deadlock), no window
  • Timeout TaskExecution:TimeoutSeconds (default 300 s) → kills the whole process tree → TimeoutException
  • Success ⇔ exit code 0 (output content is irrelevant)
  • Log row: errorMessage carries stderr (or “Command exited with code N”), durationMs, exitCode

Retry backoff (delay uses the already-incremented RetryCount)

  • Failure 1 → RetryCount 1 → wait 60 s
  • Failure 2 → RetryCount 2 → wait 120 s
  • Failure 3 → RetryCount 3 → wait 240 s
  • Failure 4+ → capped at 300 s
  • maxRetries = N → N + 1 total attempts; maxRetries = 0 → first failure = Failed

Where Hangfire sits

  • Storage = PostgreSQL (same DB as app data) → recurring schedules survive an app restart; only EF migrations run at boot
  • Server = in-process (AddHangfireServer), single default queue
  • Recurring jobs: id = task GUID, cron = task's cron string — AddOrUpdate on activate/resume/update, removed on pause/delete
  • Background jobs: manual trigger (Enqueue) and delayed retries (Schedule)
  • Dashboard: /hangfire, loopback-IP-only filter (no credentials)
06

Security

Authentication & data protection

  • JWT HMAC-SHA256 (Jwt:Secret, ≥ 32 chars), issuer TaskSchedulerAPI, audience TaskSchedulerClient, 72 h expiry; claims: user id, username, email
  • Passwords PBKDF2: 10 000 iterations, SHA-256, 16-byte salt, 32-byte hash, stored base64(salt ‖ hash)
  • [Authorize] on all task/log/dashboard endpoints; only auth, health, UI and the (loopback-only) Hangfire dashboard are open
  • Sensitive payloads redacted in logs via ISensitiveRequest (login)

Threat surface

  • Rate limit on manual trigger: fixed window 10 req/min → 429
  • Hangfire dashboard: IP filter allows 127.0.0.1/::1 only — unreachable remotely even behind a proxy
  • Secrets: none committed; appsettings.json holds empty placeholders, real values come from env vars
  • Error leakage: unknown exceptions → generic 500; validation/state errors expose their message
  • CORS: AllowAll — acceptable for this deployment shape, tighten if the UI moves to its own origin

CD workflow & deployment — .github/workflows/cd.yml

Trigger: push to main. Two jobs: docker (build + push image) and deploy (tell Railway to redeploy).

1
Job docker — build & push to GHCR
docker/login-action@v3 authenticates to ghcr.io with the automatic GITHUB_TOKEN (permissions: packages: write). docker/build-push-action@v5 builds the multi-stage Dockerfile and pushes two tags:
image tags
ghcr.io/huuquandev/task-scheduler-api:latest
ghcr.io/huuquandev/task-scheduler-api:<commit-sha>
The <sha> tag keeps every release addressable — it is the rollback handle.
2
Job deploy — Railway redeploy (needs: docker)
Calls the Railway GraphQL API with the RAILWAY_TOKEN secret. Railway then pulls the fresh image for the connected service and redeploys it (migrations auto-run when the new container boots):
deploy step — curl to Railway GraphQL
curl -s -X POST \
  -H "Authorization: Bearer ${{ secrets.RAILWAY_TOKEN }}" \
  -H "Content-Type: application/json" \
  -d '{"query": "mutation { serviceInstanceRedeploy(environmentId: "...", serviceId: "...") }"}' \
  https://backboard.railway.app/graphql/v2
The fixed environmentId/serviceId belong to this project's Railway environment and service. The only GitHub Actions secret required: RAILWAY_TOKEN.
3
What runs in the container
Multi-stage Dockerfile: mcr.microsoft.com/dotnet/sdk:10.0 (csproj-only restore layer, then publish) → mcr.microsoft.com/dotnet/aspnet:10.0 runtime, ASPNETCORE_URLS=http://+:8080, entrypoint dotnet TaskScheduler.Api.dll. .dockerignore excludes bin/, obj/, .git/, Tests/, Docs/, .env*.

Environments matrix

  • Development — Swagger ✅, auto-migrate ✅, EF/Hangfire DI ✅
  • Production — Swagger ❌, auto-migrate ✅, EF/Hangfire DI ✅
  • Testing — Swagger ❌, Hangfire dashboard ❌, auto-migrate ❌, EF/Hangfire DI ❌ (tests wire their own)
ℹ

Known issues & design notes

Documented so the next developer knows what is deliberate and what is a gap. Full list with fix ideas: ARCHITECTURE.md §14.

#IssueImpact
1Failed tasks keep their recurring job; ExecuteTask has no status guardA failed task re-runs on every cron tick and re-sends the failure email. Fix: unschedule on exhaustion, or guard at the top of ExecuteTask.
2PUT /tasks/{id} always calls RescheduleTaskAsyncUpdating a Pending task registers a recurring job → it starts running on cron without activation.
3Completed state unreachable on the execution pathSuccessful runs set the task back to Active; MarkAsCompleted/TaskCompletedEvent exist but are unused by the engine.
4UI “Re-activate” button for Failed tasksCalls POST /{id}/activate which only accepts Pending → returns 400. Align handler or remove the button.
5TaskPausedEvent has no handler; delayed retries ignore pauseA retry scheduled before a pause still fires and runs the paused task (same root cause as #1).
6Metrics & SMS are no-ops; CORS is AllowAllSeams exist (event → handler → service) but no exporter/provider is wired; tighten CORS if the UI moves off-origin.
7Dashboard deletedTasks is always 0; log DTO finishedAt non-nullable; VerifyPassword not constant-timeMinor: repo filters soft-deleted rows; AutoMapper defaults for in-flight runs; use FixedTimeEquals for hardening.
✓
Design decisions that are intentional: cron-only scheduling (no interval/one-off), single in-process Hangfire server on the default queue, one PostgreSQL database for app data + job store, loopback-only Hangfire dashboard, auto-migrations at startup, envelope-wrapped responses with app-level code.
